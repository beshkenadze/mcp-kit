# mcp-kit 0.4.0 — усыновление старых записей

Дата: 2026-11-09

## Причина

Приложения, у которых раньше был свой установщик, оставили в конфигах агентов записи с прямым путём к исполняемому файлу, например `/Applications/Undersong.app/Contents/MacOS/Undersong`. Kit 0.3.0 видит такие записи как `conflict`. Undersong обходит это в своём коде: заново прописывает пути к конфигам всех агентов (это дублирует `spec/agents.json`) и сравнивает байты файла, чтобы защититься от гонки. Это нарушает SSOT, и то же самое пришлось бы повторять в каждом приложении.

## Решение

- `MCPIntegration(..., legacyCommands: [String] = [])`: точные пути команд, которые раньше записывало само приложение.
- Запись считается **нашей**, если её `command` равен нашему симлинку или точно совпадает с одним из `legacyCommands`. Никаких догадок по имени файла или суффиксу.
- `status()` показывает наследованную запись как `outdated`.
- `connect()` заменяет наследованную запись без `force`. Проверка владения выполняется внутри `transform` у `ConfigWriter`, то есть по тем байтам, которые реально перезаписываются, поэтому гонки нет.
- `reconcile()` чинит наследованные записи автоматически, как любые `outdated`.
- `disconnect()` удаляет и наследованные записи.
- Пользовательские ключи записи сохраняются, как и раньше: kit заменяет только `command`, `args`, `env`.
- API 0.3.0 не ломается.

## Тесты

Для каждого агента (JSON и TOML):
- наследованная запись → `outdated` → `reconcile()` → `connected`, пользовательские ключи на месте;
- чужая команда остаётся `conflict` и не трогается;
- `disconnect()` удаляет наследованную запись;
- если между `status()` и записью наследованная запись сменилась на чужую, kit её не трогает и возвращает `conflict`. Проверяется через writer, который подменяет файл перед `transform`.
